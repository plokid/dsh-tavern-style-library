# 建样文库

把用户引用的文章或小说，整理成给「样文库」插件用的原文摘录库。库建好后，游玩时每轮正文都会借其中一段的**笔调**。

**条数由材料字数决定，不由「代表性」决定。** 两万字的文章只存一段，等于把整篇压成一个样本，轮换也没得换——这是最常见的失败模式，尽量避免。

## 前提：材料要由用户引用

样文库的素材来自用户在「剧本与素材库」引用的材料。引用之后，材料原文会出现在你的上下文里，你直接读上下文即可。

**不要**尝试读文件系统、不要找素材库目录、不要用 shell 命令翻文件。插件不提供这类接口，材料只能从上下文来。

用户没有引用材料时，先请他去「剧本与素材库」引用，不要凭空编造摘录。

## 流程

分两个阶段。**先把标签定下来，再动手切素材**——标签是切分依据，先切后贴会切得乱七八糟。

### 阶段一：定标签（必须先停下来等用户）

1. 调用 `style_library_list`，看现有库和现有标签池。有内容相近的库就问用户是追加还是新建，避免建一堆名字不同、内容重复的库。
2. 和用户定库的范围：一个库对应**一种笔调**或**一本书**，不要把所有材料塞进一个库混着用。
3. **读一遍材料，替这份材料拟一批笔调标签**——这是自动生成的，不用等用户说。数量看材料复杂度：

   | 材料情况 | 提议标签数 |
   |---|---|
   | 短篇、笔调统一 | 5～7 个 |
   | 中篇、笔调有起伏 | 8～12 个 |
   | 长篇、多种腔调混着 | 12～18 个 |

   标签只描述**笔调**（冷峻、留白、短句、燥热、文白、絮语、肃杀…），不描述题材、人物或情节。
   已有标签池里合适的直接复用，不要换个近义词重造一套。
4. 用 `style_tags_update`（`action: 'add'`）把它们加进标签池，然后**把清单列给用户看**，明确请他说要增、删、改哪些。

   **这一步必须停下来等用户回复**，不要自己决定完就往下走。用户说「你看着办」或「就这样」时才可以直接继续。
5. 用户提了修改就照做：加标签用 `action: 'add'`，删用 `action: 'remove'`，改名用 `action: 'rename'`（会同步改掉库里已经引用到的旧标签）。改完把最终清单再确认一次。

### 阶段二：按标签切分素材

6. 用 `style_library_split` 把材料切开（面板上的「切段预览」同款规则）。切出来的段可以直接用，但**笔调是否完整要靠你自己判断**：段落明显是一个完整场景时，宁可超长一点也不切断；反过来，一段里混了两种笔调就拆成两条。
7. **给每段定一个主标签**，从阶段一确认过的标签池里选。这段为什么是这个标签，要说得通——按笔调归，不按情节归。
8. **按标签分组排序**：同一个主标签的段落连续放在一起，标签内部再按原文先后排。这样库里的结构是「一种笔调一组」，而不是原文顺序的散点。
   轮换时同类笔调会连着出现，注入的参考风格才稳定。
9. **算要摘几条**，不要凭感觉少摘：

   | 材料字数 | 目标条数 |
   |---|---|
   | 1 千字以内 | 1～2 条 |
   | 1 千～5 千字 | 3～5 条 |
   | 5 千～1 万字 | 5～9 条 |
   | 1 万～2 万字 | 9～15 条 |
   | 2 万字以上 | 15～20 条（库上限 40 条） |

   按「材料字数 ÷ 1500」估算条数是安全的起点。**2 万字的文章只给一条是错的**——那等于把整篇的笔调压成一个样本，轮换也没得换。宁可多摘几条让用户删，也不要只交一条。
   材料特别长（超过 5 万字）时不必硬凑满 40 条，优先覆盖**笔调变化最明显的位置**（开头定调、情绪转折、场景切换、结尾收束）。
   注意容量：一条 1500 字的中文摘录约 4.4 KB，整库上限 256 KB，**别让总量超过 6 万字**。
10. 从材料里**逐字摘录**：
    - 只摘**完整的段落或场景**，能体现笔调的最小单位。不要摘句子碎片，也不要摘整章。
    - 单条 200～2000 字。原文超过 2000 字就选其中笔调最典型的几段。
    - **原文照抄**：不改标点、不改错别字、不删节、不概括、不补写。这是硬要求——注入到正文的是这段字的质感本身，改写就失去意义了。
    - **沿全文铺开**：开头、中段、后段都要有，不要只摘第一屏。长文里笔调会随情节漂移。
11. 调用 `style_library_save` 建库（库的整体标签取这批里最主要的 3～5 个），然后用 **`style_sample_save_many` 按第 8 步的分组顺序一次存入全部摘录**。每条带上它的主标签（可再加 1～2 个次要标签，每条最多 5 个）。`source` 填书名或章节。
12. 建完告诉用户：库名、条数、**按标签分组的结果**（哪个标签几条），以及每条大致出自全文哪个位置，好让用户判断要不要补。需要的话再用 `style_library_pick` 设为本局使用。

## 条数的自查

存完之后对一遍：材料有 2 万字，库里只有 1～3 条，就是没做完。这时不要直接结束，回到材料里继续摘，补到表格里对应的数量。如果材料确实只有那么多可用的完整段落（比如大量对话碎片、夹杂大段说明文），就告诉用户实际情况和为什么只能摘这么多，让用户决定。

## 建完之后

库建好只是「有样子」。用户如果还在抱怨「照着写还是不像」，或者准备长期用这个库，可以接着提炼一张风格卡：按 `distill-style-library` 那套流程分析这批复录，再把结论存进库。卡给规则，摘录给证据，两个一起注入才稳。

不要在同一次对话里顺手把卡也做了——用户还没看过摘录长什么样，先让他确认条数和分组。

## 边界

- 用户的材料里没有的内容，不要凭印象补。摘录必须能在材料里找到原句。
- 材料是写作教程、书评、分析类文章时，这类文字本身不构成「笔调样本」——它讲的是怎么写，不是写出来的样子。遇到这种情况直接说清楚，问用户要不要换成小说/散文段落。
- 材料是 JSON 或其他结构化数据时，先看清里面哪个字段是正文，只摘正文部分；结构、ID、元数据不摘。
- 用户想改已有库时，先 `style_library_list` 拿到 id 和现有内容，再决定是补摘录、删摘录还是改标签。删摘录只能用面板或直接改 JSON，工具里没有批量删。
- 用户直接说「把这几个标签加上／删掉／改个名」，直接用 `style_tags_update`，不必走完整建库流程。
- 用户的标签和你的判断冲突时**听用户的**。标签是他的分类习惯，不是客观真理；他说这段算「絮语」你就算「絮语」。

## 和其他文风功能的关系

Tavern 内置的「文风联想」每轮让后台模型现场仿写一段参考，和本插件是两套东西。同时开着会互相干扰，要提醒用户二选一。
